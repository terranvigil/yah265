# yah265 end-credits rows, 2026-11-22

A supplement to PARITY-REPORT-yah265-2026-11-12.md. It reruns that report's
"End credits" section after item 63 and doesn't change the report.

Encoder: yah265 build-rel de1f9f3d (main c5a4c8ae, item 63 merged in 52a965db), preset medium.
Reference: x265 4.3+1-e9b8812, preset medium (the anchors of 2026-10-26, binary hash 2ffa132b).
Machine: Apple M5 Max, macOS 26.6.2. Both encoders at 6 threads. Lookahead 20 on both sides.

How the rows are made: `scripts/parity_spec.py --credits`. Each tier L
title's credits span is coded on its own, at 1080p. x265 runs at CRF 28 and
ours at the 1080p cell's matched crf. Each side also runs five rungs (CRF 20,
23, 26, 29, 32), which give the size at equal PSNR-Y. PSNR-Y is the mean over
every frame. The credits mode scores PSNR-Y only, so these rows stay in the
PSNR-Y form. "extr" means the figure is extrapolated beyond the measured
points. Credits rows are supplementary. They don't gate.

## Tears of Steel: why it's still behind

The credits here are not text on black. They're stylized graphics with fine
stippled grain on every edge. The checks below ran on 240 frames from
credits frame 200 (excerpt frame 12872). Each arm ran CRF 22, 25, 28 and 31.
BD is PSNR-Y unless a row says v1. v1 is vmaf_v1.0.16 3d0h at 10 bits, with
CAMBI told the 8-bit 1920x858 encode.

| arm | BD-PSNR-Y vs x265 | BD-v1 vs x265 |
|---|---|---|
| medium (default) | +3.6% | +2.6% |
| `N265_SCREEN=0` | +3.6% (stream identical) | - |
| `N265_PSY_DARK=0` | +3.7% | - |
| `N265_PSY_DARK_LO=0` | +4.9% | - |
| `N265_CDZ=0 N265_CBQPOFFS=0 N265_CRQPOFFS=0` | +1.6% | +7.6% |
| `N265_AQ2=0 N265_AQ_BPULL=0` | +3.9% | - |
| `--aq 0` | +5.3% | - |
| `--cutree 0` | +3.9% | - |
| `--bframes 4` | +7.9% | - |
| `N265_ME_PATTERN=0` | +4.1% | - |
| `N265_RDOQ_TAIL=0 N265_TD_DIST=0` | +3.7% | - |
| 64x64 gates off | +3.4% | - |
| `N265_IRANK=0 N265_INTRA_RD_N=3 N265_TT_SKIP_INTRA=0` | +0.2% | -0.1% |
| `N265_SKIP_EXIT=1 N265_RDOQ=1` | -1.1% | -1.6% |
| `--preset slow` | -8.2% | -5.3% |

The plan's checks, in order:

- Screen typing is out. `N265_SCREEN=0` writes the same stream, byte for
  byte, at one thread and at six. No frame of the slice is typed.
- Dark psy is out. `N265_PSY_DARK=0` moves 0.03 points.
  `N265_PSY_DARK_LO` helps here: turning it off costs 1.2 points.
- The chroma trade accounts for 2.0 points of PSNR-Y. It's worth 5.0 points
  on v1, so it stays. AQ and cu-tree are ahead of the arms that turn them off.

What's left is medium's speed cuts. Two of them close the gap alone, and v1
agrees with PSNR-Y on both. The first is the intra cuts (item 34's coarse
rank, and item 57's one priced mode and dropped intra transform split). The
second is the goal-3 skip exit and RDOQ (`SKIP_EXIT 2`, `RDOQ 2`). `slow`
is far ahead. The grain on these edges is what the cheaper intra and skip
decisions miss.

The whole span (1728 frames, five rungs) confirms it:

| arm | BD-PSNR-Y vs x265 | size at x265 CRF 28's Y |
|---|---|---|
| medium (default) | +4.1% | +5.1% |
| intra cuts escaped | +1.5% | +2.1% |
| skip exit and RDOQ escaped | -0.5% | +0.2% |
| both escaped | -3.0% | -2.8% |

The default arm's five rungs are the harness's streams byte for byte.

Fix shape, not built here: gate the two cuts on content. Keep the full
intra rank and the skip exit 1 / RDOQ 1 path on frames the lookahead marks
as intra-heavy with fine texture. `N265_INTRA_RSKIP=3` already reads
intra-heavy frames this way. The knob would be 0 for main. Every tier S, M
and L cell would have to stay byte-identical, as items 61 and 62 did, and
the speed cost would need to be timed on whatever frames it fires.
Credits don't gate, so this is worth building only if story cells with
the same texture turn up.

so it's a reporting fact, not a bug.

## stem2: open

stem2's credits are white text on black, at 56-58 dB. The whole span codes
to 0.44 MB on x265 and 0.61 MB on ours. That's about 120 bytes a frame more
over 1460 frames. Per-frame overhead (slice headers, the weighted-prediction
table) would fit, but it isn't checked yet.

## Notes

- stem2 has no staged 1080p excerpt, so the credits cell couldn't be built
  before. `cred_cell` in scripts/parity_long.py now decodes the span from
  the master when no staged excerpt exists. It starts at the excerpt's
  offset plus the credits start: 5640 + 12940 = master frame 18580. That
  frame is the first black frame after the story, checked on the master's
  luma.
- Item 63's opening scan reported 18580 frames for stem2, not 12940. That
  was its own ffmpeg command, not the harness. `trim=start_frame=5640`
  without `setpts=PTS-STARTPTS` kept the source timestamps, and the
  constant-rate Y4M output filled the first 235 s with 5640 copies of
  master frame 5640. The scan's first 5641 rows are one frame. The
  harness's feeder seeks to the frame and has no such fill.
- The x265 anchors were not re-run. The x265 binary's hash matches the one
  they were coded with.
